# 用例设计方法笔记（Day2 / 2026.11.21）

## 1. 等价类划分（Equivalence Partitioning）

把输入域切成若干「处理逻辑相同」的类，每类取 1 个代表值。

**例子：登录密码（需求：6–20 位，字母+数字）**

| 类 | 类型 | 代表值 | 期望 | 用例 |
|---|---|---|---|---|
| 6–20 位合法密码 | 有效 | Abc123 | 通过校验，进入登录判定 | TC-LOGIN-018 |
| 长度 < 6 | 无效 | A | 提示「密码长度为6-20位」 | TC-LOGIN-017 |
| 长度 > 20 | 无效 | 21 位 | 截断或提示超长 | TC-LOGIN-020 |
| 空 | 无效 | 空串 | 提示「请输入密码」 | TC-LOGIN-009 |

要点：**无效等价类每条单独出一个用例**，不要「空 + 超长」合在一起测——合了以后报错只看得到第一个。

## 2. 边界值分析（Boundary Value Analysis）

缺陷最爱藏在边界。取「上点、离点、内点」：

- 密码长度：下边界 6 → 测 **5（离点）/ 6（上点）/ 7（内点）**；上边界 20 → 测 **19 / 20 / 21**。
- 手机号：固定 11 位 → 测 **10 / 11 / 12**（TC-LOGIN-015、016 就是 10 位和 12 位）。
- 库存：库存 5 件 → 测 **4 / 5 / 6**（TC-CART-003 用 5 和 6）。

我踩过的坑：一开始只写了「密码太短」一条，评审时被指出「太短」不可判定——是 1 位报错还是 5 位报错？必须写死数值。

## 3. 场景法（Use Case / 场景流）

按「基本流 + 备选流」把业务串起来：

**下单基本流**：加购 → 去结算 → 选地址 → 选优惠券 → 提交订单 → 支付成功 → 订单状态「待发货」

**备选流（每条都是一个用例）**：
- 库存不足 → TC-ORDER-007
- 未选地址 → TC-ORDER-004
- 优惠券不满足门槛 → TC-ORDER-006
- 重复点击提交 → TC-ORDER-010
- 支付超时 → TC-PAY-002
- 支付中断后继续 → TC-PAY-004
- 已支付再次支付 → TC-PAY-005

Day6 补的 5 条（TC-AFS-001~005）也是场景法：售后是「下单链路」的下游，退货时限、进度查询、取消申请都是真实用户会走的支路。

## 4. 错误推测法（Error Guessing）

靠经验列「最可能出错的地方」，我这次列的 8 类：

1. 前后空格：账号 `" 13800000000 "` → TC-LOGIN-010
2. SQL 注入：`' or 1=1--` → TC-LOGIN-013
3. XSS：`<script>alert(1)</script>` → TC-LOGIN-014、TC-SEARCH-005
4. 重复提交/连点：TC-ORDER-010、TC-PAY-010
5. 金额篡改：把支付金额改成 0.01 → TC-PAY-009
6. 验证码时效：过期验证码 → TC-LOGIN-012
7. 数量为 0 / 负数 → TC-CART-004
8. 大小写不敏感：ipad / IPAD → TC-SEARCH-007

## 5. 一条好用例的要素（八件套）

| 要素 | 不合格 | 合格 |
|---|---|---|
| 用例编号 | 「登录1」 | TC-LOGIN-001（模块缩写-三位序号） |
| 模块/功能点 | 「登录」 | 登录 / 手机验证码登录 |
| 用例标题 | 「测试登录」 | 正确账号+正确密码可登录成功 |
| 前置条件 | 无 | 已注册账号 13800000000/Abc12345，未登录状态 |
| 操作步骤 | 「登录一下」 | 1. 打开登录页 2. 输入账号 3. 输入密码 4. 点击「登录」 |
| 预期结果 | 「登录成功/显示正常」 | 1. 跳转 www.jd.com 首页 2. 右上角显示「138****0000」 3. localStorage 存在登录态字段 |
| 优先级 | 都写 P1 | P0 主流程阻挡 / P1 核心 / P2 次要 / P3 边缘 |
| 执行结果 | 空 | 通过 / 失败 / 阻塞（含原因） |

判定口诀：**把用例交给一个没做过这个项目的人，他能照着重现出同一个现象，才算合格。**
