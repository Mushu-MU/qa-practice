# 测试基础笔记（Day1 / 2026.11.21）

> 学习材料：ISTQB 基础级大纲 + 京东首页/登录页实操观察。本笔记每一条都尽量落到「我在电商站点上看到的现象」。

## 1. 软件测试的定义

IEEE 610 的定义：**在规定的条件下运行系统或组件、观察或记录结果、并对系统或组件的某个方面做出评价的过程。**

我的理解（一句话）：测试 = 用可判定的现象，证明「预期」和「实际」是否一致。三个关键词：

- **规定条件**：前置条件必须写清楚（已登录 / 有库存 / 待支付订单），否则结果不可复现。
- **可观察**：结论必须能看见、能截图、能抓包。观察不到的结论不是测试结论。
- **评价**：要么通过、要么失败、要么阻塞，没有「差不多」。

## 2. 验证（Verification）与确认（Validation）

| | 验证 | 确认 |
|---|---|---|
| 问题 | 做得对不对（符合规格） | 做的东西对不对（符合需求） |
| 电商例子 | 结算页金额 = 购物车合计 + 运费（按需求文档算得对） | 用户能不能在 3 步内下完单（真实用户走得通） |

只做验证会漏掉「规格本身就是错的需求」。

## 3. 测试七大原则（ISTQB）

1. **测试显示缺陷的存在，不能证明缺陷不存在**——65 条用例全通过也不等于没有 bug，只能说「这些路径没挂」。
2. **穷尽测试是不可能的**——手机号是 11 位数字，组合有 10^11 种，只能靠等价类 + 边界值抽样。
3. **测试尽早介入（Early testing）**——需求评审时就该问「优惠券能不能叠加」，而不是等上线前测。
4. **缺陷集群性（Defect clustering）**——80% 的缺陷集中在 20% 的模块。实操：支付、下单这种逻辑密集的模块，用例密度要高于「关于我们」这类静态页。
5. **杀虫剂悖论（Pesticide paradox）**——同一批用例重复跑，新缺陷会越来越少。所以 W1 最后一天要补 5 条新场景用例（TC-AFS-001~005）。
6. **测试活动依赖于上下文**——电商 App 测支付安全和测官网文案，投入完全不同。
7. **「没有缺陷」的谬误**——页面不报错但下单按钮藏在第 3 屏，用户找不到，这仍是产品缺陷（可用性缺陷）。

## 4. 测试分类

**按阶段**

- 单元测试：开发写，测一个函数（如「满减金额计算」）。
- 集成测试：测模块间接口（下单 → 库存扣减 → 支付回调）。
- 系统测试：整条链路（我这周的用例全部属于系统测试/功能测试）。
- 验收测试：用户视角（UAT）。

**按是否执行代码**

- 静态测试：看文档、看代码、走查（用例评审就属于静态测试）。
- 动态测试：真跑起来点（Day4/Day5 要做的事）。

**按关注点**

- 功能测试：能不能用（W1 主线）。
- 界面/易用性测试：好不好用。
- 兼容性测试：Chrome / Edge / 手机端表现是否一致。
- 性能测试：并发下会不会挂。
- 安全测试：SQL 注入、XSS、越权、金额篡改（我写了 TC-LOGIN-013/014、TC-SEARCH-005、TC-PAY-009 四个安全相关用例）。
- 接口测试：绕过 UI 直接打 API（W2 主线）。

**按代码可见性**

- 黑盒（只关心输入输出，W1 全部是黑盒）
- 白盒（关心分支覆盖）
- 灰盒（接口测试常属此类）

## 5. 测试流程（我做 W1 的骨架）

```
需求/场景理解 → 测试计划(范围/优先级) → 用例设计 → 用例评审
   → 执行(通过/失败/阻塞) → 缺陷记录与跟踪 → 回归 → 测试报告/复盘
```

- **测试计划**决定「测什么、不测什么」。W1 我明确不测：性能、多语言、真实支付扣款。
- **用例评审**放在执行前，成本最低（Day3 做的事）。
- **回归**指修完 bug 后重跑相关用例，并确认没引入新问题。

## 6. 七个原则怎么落到我的 65 条用例上

| 原则 | 在用例表里的体现 |
|---|---|
| 穷尽不可能 | 手机号只取 10 位 / 11 位 / 12 位三个边界（TC-LOGIN-015/016），不穷举 |
| 缺陷集群 | 登录 20 条 + 支付 10 条，占了 65 条的 46% |
| 杀虫剂悖论 | Day6 补了售后 5 条新场景（TC-AFS-001~005） |
| 没有缺陷的谬误 | 写了体验类预期（如 TC-SEARCH-004 无结果页要有推荐引导，不能只空白） |
| 尽早介入 | 用例评审记录里改了 5 条「无法判定」的预期结果 |
